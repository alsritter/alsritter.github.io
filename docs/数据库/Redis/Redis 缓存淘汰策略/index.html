Redis 缓存淘汰策略

1. 请描述缓存数据处理的完整流程​

这是一道考察对缓存基础理解的题目，主要看候选人是否理解缓存的工作原理。

流程说明：

  1. 缓存命中：用户请求的数据在缓存中存在，直接从缓存返回，响应速度最快
  2. 缓存未命中：缓存中不存在数据，需要查询数据库
  3. 数据库查询：从持久化存储层获取数据
  4. 缓存更新：将查询到的数据写入缓存，为下次请求做准备
  5. 响应用户：返回最终结果

架构对比：

  • 左侧（无缓存）：客户端直接访问存储层，性能受限于数据库
  • 右侧（有缓存）：增加缓存层后，大部分请求可以从内存快速响应

2. 分析缓存架构的收益和成本​

这道题考察候选人对缓存技术的全面理解，不仅要知道优点，也要了解引入缓存的代价。

收益分析：

  1. 加速读写性能

    • 缓存通常基于内存，读写速度远超磁盘存储
    • Redis QPS 可达 10万+，MySQL 通常只有几千
    • 显著优化用户体验，降低响应延迟

  2. 降低后端负载

    • 减少数据库访问频次，降低 DB 压力
    • 避免复杂 SQL 的重复计算（如多表联查、聚合计算）
    • 提高系统整体吞吐量

成本分析：

  1. 数据一致性问题

    • 缓存与数据库间存在数据不一致窗口期
    • 需要设计合适的缓存更新策略
    • 对强一致性业务场景有挑战

  2. 代码维护成本

    • 需要同时处理缓存层和存储层逻辑
    • 增加了缓存失效、更新等复杂逻辑
    • 调试和排错难度增加

  3. 运维成本

    • 需要额外的缓存集群维护（如 Redis Cluster）
    • 监控指标增加（命中率、内存使用等）
    • 故障处理复杂度提升

适用场景：

  • 复杂计算场景：大量联表操作、统计分析等耗时查询
  • 高频访问场景：即使单次查询很快，但访问频次极高的数据

3. Redis 支持哪几种缓存淘汰策略？各有什么特点？​

这是核心面试题，考察对 Redis 内存管理机制的深度理解。

LRU (Least Recently Used) - 最近最少使用​

工作原理：

  • 每个 key 维护最后访问时间戳
  • 内存不足时，优先淘汰最久未被访问的数据
  • 适合有时间局部性的访问模式

Redis 中的 LRU 策略：

  • allkeys-lru：从所有 key 中使用 LRU 算法淘汰
  • volatile-lru：仅从设置过期时间的 key 中使用 LRU 淘汰

LFU (Least Frequently Used) - 最少频率使用​

工作原理：

  • 每个 key 维护访问频次计数器
  • 内存不足时，优先淘汰访问频次最低的数据
  • 更好地保护热点数据

Redis 中的 LFU 策略：

  • allkeys-lfu：从所有 key 中使用 LFU 算法淘汰
  • volatile-lfu：仅从设置过期时间的 key 中使用 LFU 淘汰

FIFO (First In First Out) - 先进先出​

工作原理：

  • 按照数据进入缓存的时间顺序进行淘汰
  • 最先进入的数据最先被淘汰
  • 实现简单，但可能淘汰热点数据

其他淘汰策略​

Redis 完整的淘汰策略：

  • noeviction：不淘汰，内存满时返回错误（默认）
  • allkeys-random：从所有 key 中随机淘汰
  • volatile-random：从设置过期时间的 key 中随机淘汰
  • volatile-ttl：优先淘汰 TTL 最短的 key

4. 如何选择合适的缓存淘汰策略？​

业务场景分析：

  1. 热点数据访问模式

    • 推荐使用 allkeys-lru 或 allkeys-lfu
    • LFU 更适合长期稳定的热点数据
    • LRU 更适合有时间局部性的访问

  2. 周期性访问模式

    • 可考虑 volatile-ttl 结合合理的过期时间设置
    • 让数据在业务周期结束时自动过期

  3. 随机访问模式

    • 可使用 allkeys-random
    • 适合访问模式完全随机的场景

配置示例：

# 设置最大内存
CONFIG SET maxmemory 1gb

# 设置淘汰策略为 LFU
CONFIG SET maxmemory-policy allkeys-lfu

# 设置 LFU 相关参数
CONFIG SET lfu-log-factor 10
CONFIG SET lfu-decay-time 1

6. 在生产环境中如何配置 Redis 缓存淘汰策略？​

这道题考察实际运维经验和最佳实践。

推荐配置组合：

  1. 低一致性业务
# 设置最大内存和淘汰策略
maxmemory 4gb
maxmemory-policy allkeys-lfu
  1. 高一致性业务
# 结合超时剔除和主动更新
maxmemory 4gb
maxmemory-policy volatile-lru
# 同时在应用层实现主动更新机制

配置修改步骤：

  1. 编辑 redis.conf 配置文件
  2. 定位 maxmemory-policy 参数
  3. 修改为目标策略（如 allkeys-lfu）
  4. 重启 Redis 服务使配置生效

注意事项：

  • 不同算法适用于不同访问模式
  • 需要结合业务特点选择合适策略
  • 生产环境建议先在测试环境验证效果

7. 缓存粒度控制的考量因素有哪些？​

这道题考察缓存设计的深度思考能力。

场景分析： 假设视频表有 100 个字段，如何设计缓存粒度？

评估维度对比：

维度全量数据部分数据
通用性✅ 高：一次缓存，多处使用❌ 低：需求变化时需要调整
空间占用❌ 大：缓存大量无用字段✅ 小：只缓存必要数据
代码维护✅ 简单：字段变更无需改代码❌ 复杂：新增字段需要刷新缓存
网络传输❌ 慢：传输大量无用数据✅ 快：传输数据量小

最佳实践建议：

  1. 核心业务数据：采用全量缓存，保证通用性
  2. 大字段数据：分离存储，按需缓存
  3. 统计类数据：只缓存计算结果，不缓存原始数据
  4. 设置合理的 TTL：避免缓存数据过度堆积

8. 设计一个带有 Nginx 的多层缓存架构​

这是一道综合性架构设计题，考察对多层缓存的理解。

多层缓存优势：

  1. Nginx 层：静态资源缓存，减少应用服务器压力
  2. Redis 层：动态数据缓存，减少数据库访问
  3. 分层防护：多层过滤，显著提升整体性能

配置要点：

  • Nginx 缓存：适合静态内容和短期不变的动态内容
  • Redis 缓存：适合频繁变化的业务数据
  • TTL 设置：Nginx TTL < Redis TTL，保证数据一致性
